# Prompt v2 and run-to-run stability (2026-09-25)

**Question 1:** does prompt v2 fix run 1's main finding? In run 1, vague phrases such as
"a predefined number" were recorded as if they were stated values.

**Question 2:** how stable is extraction between runs, given that the sampling temperature
can't be fixed on current models?

**Setup:** two runs of the 20 gold-set provisions with prompt `2026-09-25.2`
(`eval/runs/v2-a`, `eval/runs/v2-b`), compared with run 1 (prompt `2026-09-25.1`,
the reviewed catalog). Model: `claude-opus-5` for every record. Prompt v2 changed one
rule only.

## 1. Effect of the prompt change

| Metric | v1 | v2-a | v2-b |
|---|---|---|---|
| Requirements | 74 | 85 | 74 |
| Quote validity | 1.00 | 1.00 | 1.00 |
| Obligation recall | 1.00 | 1.00 | 1.00 |
| Granularity in gold range | 0.95 | 1.00 | 0.95 |
| Testability accuracy | 0.88 | 0.87 | 0.91 |
| Invented specificity | 0.00 | 0.00 | 0.00 |
| **Vague stated values** | **0.365** | **0.047** | **0.068** |

The fix worked: vague stated values fell by about 85%, and no other metric got worse.
Every remaining case is "where appropriate" recorded as a *condition*
(`update_condition: where appropriate`). That's a defensible reading. If it should also
become `entity_defined`, the next prompt version needs to name that phrase explicitly.

## 2. Stability (v2-a against v2-b)

| Metric | Score |
|---|---|
| Provisions with the same requirement count | 18 / 20 |
| Mean clause overlap | 0.94 |
| Testability agreement on matched clauses | 0.95 |

Instability is concentrated, not spread out:

- **9.2 (cryptography policy):** 15 requirements in run A, 3 in run B. The provision
  nests (i)–(xii) inside point (c). Whether to split sub-items is a judgement the prompt
  leaves open, and the model decides it differently between runs. The gold range
  (1–16) accepts both, so only the run comparison detects this.
- **3.2.1:** 2 against 3 requirements. Run B separated "respond accordingly to mitigate
  the impact" from the detection obligation.
- **Testability flips** occur on the same ambiguous points as in run 1, most of all
  6.6.1 (patch procedures: documentary or technical, 3/5 agree).

The main source of variation is **granularity on nested lists**, not what the model
reads into the text. Every run found the same clauses (recall 1.00 each time) with
verbatim quotes and no invented values.

## Conclusions

1. Keep prompt v2 for any further extraction.
2. Before extracting provisions with deep nesting (9.2, and similar lists in 5.1 and
   6.2), add an explicit splitting rule, for example "roman-numeral sub-items stay
   within their lettered point", and measure again. The gold set should also label
   granularity more tightly where nesting occurs.
3. The 74 reviewed v1 requirements keep their v1 parameter values. They were approved as
   written. Reprocessing them would mean reviewing them again.

## Limits

Two runs per prompt version is a minimum, not a distribution. The stability figures show
where variation happens, not how often.
